# ArtistOS Hoo

Booking/CRM app for freelance artists (mehndi/makeup studios and similar) — customers, services, bookings, calendar, a client-facing portfolio with shareable links, Razorpay payments, and web push booking reminders.

Next.js App Router + Supabase (Postgres) + Cloudflare R2, with fully custom phone/password auth (not Supabase Auth).

## Getting started

```bash
pnpm install
pnpm dev          # dev server (Turbopack)
pnpm build        # production build
pnpm start        # run the production build
pnpm lint         # eslint (flat config)
```

Package manager is **pnpm** (see `packageManager` in `package.json`). No test runner is configured.

## Database migrations (Supabase CLI)

Schema lives in `supabase/migrations/*.sql` as timestamp-prefixed files applied **in filename order**.

### One-time setup

These commands talk to the **hosted** project. Docker is not required — that's only for the optional local stack further down.

```bash
# No install needed: npx supabase <command> works.
# To install globally instead, grab the .deb from
# https://github.com/supabase/cli/releases  (Ubuntu), or `brew install supabase/tap/supabase` (macOS).

npx supabase login --token sbp_xxx         # token from supabase.com/dashboard/account/tokens
                                           # (plain `supabase login` opens a browser instead)
npx supabase init                          # creates supabase/config.toml
npx supabase link --project-ref <your-project-ref>
```

Your project ref is the subdomain of your Supabase URL — for `https://abcdefgh.supabase.co` the ref is `abcdefgh`; it's in `NEXT_PUBLIC_SUPABASE_URL`. Linking prompts for the database password (Project Settings → Database).

If linking fails on connection, some networks can't reach Supabase's direct IPv6 endpoint — fall back to pasting the migration SQL into the dashboard's SQL editor, running files in filename order.

### ⚠️ First push: repair the migration history

Migrations in this repo were historically applied **by hand in the Supabase SQL editor**, so the remote `supabase_migrations.schema_migrations` table has no record of them. A plain `supabase db push` would try to re-run all of them.

Check what the remote thinks is applied:

```bash
supabase migration list
```

For every migration already applied to your database, mark it applied **without running it**:

```bash
npx supabase migration repair --status applied \
  20240101000001 20240101000002 20240101000003 20240101000004 \
  20240101000005 20240101000006 20260723114800 20260727131900 \
  20260731000001 20260801000001 20260801000002
```

Only repair the ones you have actually applied — run `supabase migration list` first to see where you stand. Re-run it afterwards; local and remote should line up except for anything genuinely new.

### Applying migrations

```bash
npx supabase db push --dry-run    # show what would run, change nothing
npx supabase db push              # apply pending migrations to the linked project
npx supabase migration list       # local vs remote status
```

Always `--dry-run` first and confirm only the files you expect are listed.

### Adding a migration

```bash
supabase migration new create_something_table
```

This creates `supabase/migrations/<timestamp>_create_something_table.sql`. Write plain SQL into it.

**The leading timestamp is the migration's identity, so it must be unique.** Two files sharing a version — easy to do when hand-naming files like `20260801000001_*.sql` — will break `db push`. Prefer `supabase migration new`, which stamps the real current time.

House style, matching the existing files:

- `create table if not exists public.<name> (...)` with `bigint generated by default as identity primary key`
- `user_id bigint not null references public.users(id) on delete cascade`
- `created_at` / `updated_at` as `timestamp with time zone default timezone('utc'::text, now()) not null`
- an index on `user_id` and on any foreign key you filter by
- an `updated_at` trigger:

  ```sql
  drop trigger if exists <name>_set_updated_at on public.<name>;
  create trigger <name>_set_updated_at
  before update on public.<name>
  for each row
  execute function public.set_updated_at();
  ```

### Local database (optional)

```bash
supabase start                # Postgres + Studio in Docker
supabase db reset             # drop and replay every migration from scratch
supabase stopx
```

`db reset` is the best way to prove your migrations apply cleanly in order before pushing to a real project.

## Environment variables

Copy into `.env` (gitignored). Everything except the push block already existed.

| Variable                                                                                           | Purpose                                                                             |
| -------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`                                        | Supabase Postgres client                                                            |
| `JWT_SECRET` / `AUTH_SECRET`                                                                       | Signs the custom `artist_session` token                                             |
| `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET_NAME`                      | Portfolio file storage                                                              |
| `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `NEXT_PUBLIC_RAZORPAY_KEY_ID`, `RAZORPAY_WEBHOOK_SECRET` | Storage plan payments                                                               |
| `STORAGE_*`                                                                                        | Free tier size, share expiry, max upload size                                       |
| `CRON_SECRET`                                                                                      | Bearer token guarding every `/api/cron/**` route                                    |
| `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `NEXT_PUBLIC_VAPID_PUBLIC_KEY`, `VAPID_SUBJECT`           | Web push                                                                            |
| `BOOKING_REMINDER_MINUTES_BEFORE`                                                                  | How far ahead of a booking to remind (default 60)                                   |
| `NOTIFICATION_MAX_ATTEMPTS`                                                                        | Dispatcher retry budget per notification (default 3)                                |
| `APP_TIMEZONE`                                                                                     | Timezone that `booking_date` + `start_time` are written in (default `Asia/Kolkata`) |

Generate VAPID keys with:

```bash
npx web-push generate-vapid-keys
```

`VAPID_PUBLIC_KEY` and `NEXT_PUBLIC_VAPID_PUBLIC_KEY` hold the **same** value — the second is the client-exposed copy used by `pushManager.subscribe`.

> `CRON_SECRET` is checked as `if (cronSecret && secret !== cronSecret)`. If the variable is unset, the cron routes are **unauthenticated**. Always set it in production.

## Scheduled jobs

`vercel.json` defines three crons, all `GET` routes requiring `Authorization: Bearer $CRON_SECRET`:

| Route                                   | Schedule    | Job                                                               |
| --------------------------------------- | ----------- | ----------------------------------------------------------------- |
| `/api/cron/notifications/scan-bookings` | every 5 min | Enqueues reminders for bookings whose reminder moment has arrived |
| `/api/cron/notifications/dispatch`      | every 2 min | Sends every pending row in `notification_events`                  |
| `/api/cron/portfolio/expire-shares`     | daily 03:00 | Sweeps expired portfolio share links                              |

Trigger one by hand:

```bash
curl -H "Authorization: Bearer $CRON_SECRET" \
  http://localhost:3000/api/cron/notifications/scan-bookings
```

**Vercel's Hobby plan only permits daily crons** — the minute-level schedules above need Pro, or an external scheduler (GitHub Actions cron, cron-job.org) hitting the same URLs with the same header.

## Notifications architecture

Producers write rows into `notification_events`; a dispatcher cron drains the table and pushes to whoever the row names. The dispatcher never touches `bookings`, so new producers (admin broadcasts, other server events) plug in without changing it.

A row in `notification_events` means **ready to send now** — there is no `scheduled_for`. Producers only insert once the moment has arrived.

- `lib/push/` — transport: VAPID config, the `web-push` singleton, subscription CRUD, sending. A 404/410 from the push service deletes the dead subscription rather than throwing.
- `lib/notifications/` — the queue: enqueue/claim/mark, plus `producers/bookings.ts`, the only booking-aware piece.

The booking scanner's eligibility test is deliberately overdue-tolerant — "the reminder moment has passed **and** the booking hasn't started" rather than a narrow "due in the next N minutes" window. A missed cron run makes a reminder late, not silently lost.

Artists opt in per device from **Profile → Notifications**, and the "Send test notification" button pushes to that one device only (bypassing the queue, so feedback is immediate).

> iOS only delivers web push to PWAs installed to the home screen. On iPhone, "Add to Home Screen" first or the toggle cannot work.

## Non-standard Next.js

This repo pins a Next.js version where **`middleware.ts` is renamed to `proxy.ts`**, exporting `proxy()` instead of `middleware()`. Route protection lives in [proxy.ts](proxy.ts). Do not create a `middleware.ts` — it will not run. When an API behaves unexpectedly, check `node_modules/next/dist/docs/` for the pinned version's docs rather than relying on training-data behaviour.
